# 측정 기록

## 2026-11-16: 첫 구현과 gksdud 2.1.1 의 비교

기기: MacBook(Apple Silicon, 8 CPU), macOS 27.2(26B123), rustc 1.100.0, 릴리스 프로필
(`opt-level=3`, thin LTO, `panic=abort`, strip).

**기기 상태가 나빴다.** 재는 내내 다른 작업(OrbStack 가상 머신 CPU 315%)이 돌아 `uptime` 의 부하
평균이 181~511 이었고, 화면은 잠겨 있었다(gksdud 가 잠금 중에 자기 키 매핑을 걷어 둔 상태였다).
시간 값은 참고로만 읽는다.

### 잰 것

hanyeong 의 실행 중 값과 두 도구의 지연을 재지 못한 이유:

- 이 셸에 접근성 권한이 없다(`hanyeong status` 가 `접근성 권한: 없음`). `run` 과 `probe` 는 이벤트 탭을
  만들고 키 이벤트를 보내야 해서 시작하지 못한다.
- gksdud 가 돌고 있다. 함께 돌면 서로의 키를 주고받으므로 `run` 이 거부한다.
- 화면이 잠겨 있었다. 잠금 화면에서는 키 이벤트가 탭에 오지 않는다.

권한을 주고 gksdud 를 끈 뒤 화면이 열린 상태에서 아래를 돌리면 표의 빈칸이 채워진다.

```sh
tools/measure_live.sh gksdud outputs/live-gksdud        # gksdud 가 켜진 채로
# gksdud 종료 → 아무 도구도 없는 상태
tools/measure_live.sh none outputs/live-none
./target/release/hanyeong run &                         # 다른 터미널에서
tools/measure_live.sh hanyeong outputs/live-hanyeong
```

### 구조에서 오는 차이 (재지 않았다. 코드에서 읽은 것이다)

- gksdud 는 1초마다 키 매핑을 훑는다(원본 `docs/tricks.md` "1초마다 매핑을 확인"). 위의 60초에
  0.30초라는 CPU 시간에는 이것이 들어 있을 것이다. hanyeong 은 30초에 한 번, 그리고 키보드가 붙었을
  때만 확인한다(`crates/hanyeong-core/src/recheck.rs`).
- gksdud 의 탭은 키 누름·뗌, 수정키 변화, 마우스 누름 세 종류를 받는다(원본 `main.swift:914`).
  hanyeong 의 탭은 키 누름·뗌만 받고, 대상 키가 아니면 키 코드 하나를 읽고 돌려준다
  (`crates/hanyeong-mac/src/tap.rs` 의 `callback`).

## 2026-11-16 (이어서): 실기기 측정

첫 구현의 릴리스 빌드. 접근성 권한이 있는 터미널 패널에서 `tools/measure_live.sh` 로 쟀다.
gksdud 는 5일 넘게 켜져 있던 프로세스이고 hanyeong 은 막 띄운 것이다. 부하 평균은 재는 동안
50~84 였다(OrbStack). **지연 값은 잡음이 크다**: 같은 측정의 최소와 중앙값이 3~6배 벌어진다.

읽는 법:

- 메모리와 스레드는 부하와 무관하고 차이가 크다. hanyeong 이 약 9분의 1 이다.
- 키 통과 지연은 세 측정을 차례로(동시에가 아니라) 쟀고 부하가 계속 바뀌었다. "도구 없음"보다
  hanyeong 이 0.5 ms, gksdud 가 2.6 ms 더 걸린 것으로 나왔지만, 이 차이가 도구 때문인지 그 순간의
  부하 때문인지 이 한 번으로는 가를 수 없다. 조용한 기기에서 번갈아 여러 번 재야 한다.
- CPU 시간은 한 번씩만 쟀다. 방향(hanyeong 이 적다)은 1초 훑기가 없다는 구조와 맞지만 배율을 말할
  근거는 아니다.

### 전환 지연은 재지 못했다

`probe --mode switch` 는 F19 를 누르고 `TISNotifySelectedKeyboardInputSourceChanged` 알림을 기다린다.
두 도구 모두에서 대부분 1초 안에 알림이 오지 않았다: gksdud 40번 중 26번, hanyeong 40번 중 29번,
다시 잰 20번 중 14번. hanyeong 은 처음 6~8번만 연달아 잡히고(84~133 ms) 그 뒤로 끊겼다.
hanyeong 자신의 집계는 `전환 43번`(probe 40번 + 그 밖 3번)이었으므로 탭은 누름을 받아 다시 보냈다.
알림이 오지 않은 것이 실제로 전환이 안 된 것인지, 알림이 빠진 것인지는 확인하지 못했다. 이 측정
방법을 믿을 수 없으므로 전환 지연의 숫자는 내지 않는다. 다음에는 알림 대신 입력 소스를 직접
읽어(`TISCopyCurrentKeyboardInputSource`) 확인해야 한다.

### 실기기에서 처음 돌려 확인한 코드

- `hanyeong run`: 단축키 60번을 ⌃Space `[32, 49, 262144]` 에서 F19 `[65535, 80, 0]` 로 쓰고
  (`hotkey.rs` 의 쓰는 길), 키보드 3대에 매핑을 걸고, `준비됐습니다` 까지 갔다.
- SIGTERM 으로 끝내자 `키보드 3 대의 키 매핑을 되돌렸습니다`, `입력 소스 단축키를 원래대로
  되돌렸습니다` 가 나왔고, `status` 가 단축키 `[32, 49, 262144]`, 매핑 0대를 보여 줬다. 두 번 반복했다.
- gksdud 를 정상 종료(`osascript … to quit`)하면 gksdud 도 자기 것을 되돌린다. 그 뒤에 hanyeong 을 띄웠다.
- 사용자가 우측 ⌘ 으로 직접 전환해 보고 "잘 돼"라고 확인했다(2026-11-16, 첫 구현의 빌드).
  툴팁 상자가 사라졌는지는 따로 묻지 않았고, hanyeong 은 화면에 그리는 것이 없다.

### 알려진 문제: 바쁜 기기에서 폭주 차단이 잘못 걸린다

측정 중 `폭주 차단 1번`이 두 번 나왔다(probe 의 누름 간격은 250~400 ms 였다). `PressGate` 에 넣는
시각이 콜백이 불린 시각이라, hanyeong 이 CPU 를 못 받아 밀린 누름들이 한꺼번에 도착하면 60 ms 안의
여섯 번으로 보인다. 그러면 2초 동안 F19 를 그대로 통과시킨다(전환은 되지만 뗄 때 된다).

이벤트가 만들어진 시각(`CGEventGetTimestamp`)으로 바꿔 봤으나 되돌렸다: 합성 이벤트의 그 값은
단위가 달라 보였고(400 ms 간격의 누름 20번에서 다시 폭주 1번), 값이 0 인 이벤트는 계속 폭주로
보이게 된다. 고치려면 두 시각을 모두 넣어 둘 다 구간 안일 때만 폭주로 보아야 한다
(`hanyeong-core` 의 판단이 바뀌는 변경이다).

## 2026-11-16 (이어서): 폭주 차단 오판 수정

`PressGate` 가 도착 시각과 만든 시각을 둘 다 보고, 둘 다 60 ms 구간 안일 때만 폭주로 본다
(`crates/hanyeong-core/src/press.rs` 의 `storm`). 탭은 `CGEventGetTimestamp` 를 함께 넘긴다.

- 재현 테스트 `presses_that_were_delayed_and_arrive_together_are_not_a_storm` 는 고치기 전에
  실패했다(`left: Pass, right: Switch`). 고친 뒤 통과한다. 합성 이벤트(만든 시각 0, 틱 단위)와
  본뜬 이벤트의 주고받기를 다루는 테스트 둘을 함께 넣었다. Rust 테스트 40건 통과.
- **실기기 확인은 하지 못했다.** 고친 빌드를 띄우고 `probe --mode switch --count 20` 을 돌렸으나
  화면이 잠겨 있어(`CGSSessionScreenIsLocked = true`) 키 이벤트가 탭에 오지 않았다: probe 는 20번 모두
  놓쳤고 hanyeong 의 집계는 `전환 0번, 폭주 차단 0번`이었다. 이 실행은 수정에 대해 아무것도 말해
  주지 않는다. 띄우기·되돌리기·다시 띄우기는 이 빌드에서도 됐다.

## 2026-11-16 (이어서): 메뉴바 아이콘과 로그인 자동 실행

`run` 이 메뉴바에 `한` 아이콘을 올린다(`crates/hanyeong-mac/src/tray.rs`). 메뉴는 `일시정지`/`다시 켜기`와
`hanyeong 종료`. 툴팁은 없다. `tools/install.sh` 가 `~/Applications/hanyeong.app` 으로 묶어 임시 서명하고
LaunchAgent `dev.hanyeong` 으로 등록한다.

| 항목 | 아이콘 없음(첫 구현) | 아이콘 있음 | gksdud 2.1.1 |
|---|---|---|---|
| 메모리(phys_footprint) | 3.3 MB | 12 MB | 30 MB |
| 스레드 | 2 | 6 | 4 |
| 실행 파일 크기 | 416,544 B | 417,168 B | 3,284,928 B |

띄운 지 5초 뒤에 `footprint`, `top -stats threads` 로 한 번 쟀다. AppKit 을 불러오는 값이다.

실제로 돌려 본 것: 터미널에서 띄워 `준비됐습니다` 까지 갔고, SIGTERM 으로 AppKit 의 이벤트 루프가
끝나 매핑과 단축키를 되돌렸다. `tools/install.sh` 뒤 `launchctl print` 가 `state = running` 이고,
로그에 접근성 권한을 기다린다는 줄이 나왔다(번들은 터미널과 따로 권한을 받아야 한다).

**확인하지 못한 것**: 아이콘이 실제로 보이는지, 메뉴의 일시정지와 종료가 동작하는지(화면을 볼 수단이
없다), 번들에 권한을 준 뒤의 동작, 재부팅·재로그인 뒤 자동으로 뜨는지.

## 2026-11-16 (이어서): 설치본이 권한을 받지 못한 문제

사용자가 설치 뒤 "한영 전환이 안 되고, 아이콘도 아무 화면도 보이지 않는다"고 알렸다. 설치본은
`접근성 권한이 없습니다 … 10분 동안 기다립니다` 를 남기고 프로세스 안에서 기다리고만 있었고
(`launchctl print`: `runs = 1`, `state = running`), 권한이 없으면 매핑도 아이콘도 올리지 않았다.
같은 빌드를 권한 있는 터미널에서 띄우자 전환이 됐고 사용자가 `한` 아이콘이 보인다고 확인했다:
아이콘 코드는 정상이고 문제는 설치본의 권한이다.

고친 것(`crates/hanyeong/src/app.rs` 의 `check_trust`, `tools/install.sh`): 권한이 없으면 한 번만 손쉬운
사용 화면을 열고(`trust.prompted` 로 기억), 5초 쉬고 실패로 끝낸다. LaunchAgent 는
`KeepAlive = {SuccessfulExit = false}`, `ThrottleInterval = 10` 으로 다시 띄운다. 권한 확인을 경쟁 도구
확인보다 먼저 한다.

**아직 풀리지 않았다.** 다시 설치한 뒤 9분 동안 60번 다시 떴지만 매번 권한이 없었다
(`runs = 60`, `last exit code = 1`). 사용자가 그동안 목록에서 켰는지는 모른다. 접근성 권한 목록은
읽을 수 없었다(`TCC.db: authorization denied`). 켰는데도 이렇다면 임시 서명한 번들을 launchd 가 직접
띄울 때 권한이 다른 대상에 붙는 것이고, 그때는 고정 서명이나 `open -a` 로 띄우는 길을 봐야 한다.

## 2026-11-16 (이어서): 설치본의 권한 문제의 원인과 해결

원인은 손쉬운 사용 목록에 남은 옛 등록이었다. 첫 설치의 빌드로 `dev.hanyeong` 이 등록된 뒤 내용이
바뀐 빌드를 다시 설치했고, 임시 서명한 앱의 권한은 그 빌드에 묶여 있어 맞지 않았다. 사용자가 앱을
목록에 다시 더해도 그대로였다(`open -a … --args status` 로 띄운 설치본이 `접근성 권한: 없음`).
사용자가 `tccutil reset Accessibility dev.hanyeong` 을 돌리고 다시 더하자 같은 확인이
`접근성 권한: 있음` 이 됐다.

그 뒤 터미널 쪽을 끄고 LaunchAgent 를 올리자 설치본(`~/Applications/hanyeong.app/Contents/MacOS/hanyeong run`)
이 키보드 3대에 매핑을 걸고 `준비됐습니다` 를 남겼다. `status`: 단축키 `[65535, 80, 0]`, 3대 중 3대.
재부팅·재로그인 뒤에 뜨는지는 아직 보지 못했다.

앱 아이콘을 만들었다(`assets/icon.svg` → `tools/make_icon.py` → `assets/AppIcon.icns`). 설치 스크립트가

  잠자기는 막지 않는다. App Nap 이 실제로 걸려 있었는지와 꺼졌는지는 root 권한이 없어 보지 못했다.

옛 빌드(0.1.2)와 새 빌드를 `hanyeong install` 로 번갈아 설치하며 2바퀴 쟀다. probe 는 새 빌드의 것을
터미널 패널에서 돌렸다.

## 2026-11-26 16:19: 실제 누름의 대기 기록

전환한 누름마다 키가 만들어진 시각과 탭 콜백이 불린 시각의 차이를 모은다(`hanyeong_core::lag`).
시스템(WindowServer, 앞선 탭)과 hanyeong 이 CPU 를 받기까지 기다린 시간이고, 시스템이 입력 소스를 바꾸는
시간은 들어 있지 않다. 콜백은 탭 스레드의 분포에 넣고(메인 스레드가 가져가는 중이면 다음 누름 때),
메인 스레드가 30초마다 매핑을 확인할 때 가져가 50 ms 이상인 누름이 있었으면 로그에 한 줄 남긴다. 끝날 때
실행 전체의 분포를 남긴다.

만든 시각의 단위: 합성 이벤트에서는 mach 틱이었고, 하드웨어 키는 확인하지 못했다. 나노초와 틱 두 해석
가운데 지금보다 앞이고 10초 안인 것을 고른다. 둘 다 아니면 `잴 수 없음` 으로 센다.

실기기(부하 평균 41): 새 빌드를 설치하고 `probe --mode react --count 20` 으로 합성 F19 를 20번 넣은
뒤 `launchctl kickstart -k` 로 정상 종료시켰다.

```
hanyeong: 전환 20번, 폭주 차단 0번, 탭 꺼짐 0번
hanyeong: 한영 키가 hanyeong 에 닿기까지: 20번, 50 ms 이상 0번, 가장 늦은 것 21.4 ms, 잴 수 없음 0번 (0~5 ms 17 · 5~10 ms 1 · 10~20 ms 1 · 20~50 ms 1 · 50~100 ms 0 · 100~200 ms 0 · 200~500 ms 0 · 500 ms~ 0)
```

같은 실행에서 probe 쪽 react 는 중앙값 4.23 ms, 최대 220.7 ms 였다. hanyeong 에는 20번 모두 21.4 ms 안에
닿았으므로, 그 220 ms 는 hanyeong 에 닿은 뒤(다시 보낸 누름이 probe 에 돌아가는 길이나 probe 자신)의 것이다.

확인하지 못한 것: 하드웨어 키의 만든 시각이 읽히는지(사용자가 실제로 눌러야 한다. `잴 수 없음` 이 늘면
읽히지 않는 것이다), 30초마다의 `늦게 닿았습니다` 줄(이번에 50 ms 넘은 누름이 없었다).

## 2026-11-26 17:36: 우선순위에 따른 깨어남 지연

전환이 늦는 것이 우선순위 때문인지 가르려고, 우선순위만 다른 스레드 넷을 한 프로세스에서 동시에 60초
돌렸다. 각 스레드는 5 ms 마다 `mach_wait_until` 로 잠들고, 정한 시각보다 얼마나 늦게 깨어났는지 잰다
(저장소 밖의 일회용 프로그램. 터미널 패널에서 실행). 부하 평균 109 → 145.

| 스레드 | 실제 우선순위(`ps -M`) | 깨어남 수 | 중앙값 | p99 | 최대 | 10 ms 이상 | 50 ms 이상 | 100 ms 이상 |
|---|---|---|---|---|---|---|---|---|
| 기본 | 31 | 5,322 | 3.41 ms | 51.3 ms | 192.0 ms | 796 | 56 | 10 |
| QoS user-interactive 요청 | 31 | 5,314 | 3.41 ms | 51.7 ms | 192.0 ms | 819 | 55 | 9 |
| 실시간(`THREAD_TIME_CONSTRAINT_POLICY`, 계산 0.5 ms / 제한 1 ms) | 97 | 11,963 | 0.01 ms | 0.18 ms | 0.6 ms | 0 | 0 | 0 |

- 터미널에서 띄운 프로세스는 QoS 요청이 31 로 눌렸다. hanyeong 설치본의 탭 스레드(37)와 같은 값은 재지
  못했다. 37 도 CPU 를 쓰던 46~47 의 스레드들보다 아래라 31 과 비슷할 것으로 보지만 추론이다.
- 이 부하에서 실시간이 아닌 스레드는 깨어남의 약 1% 가 50 ms 이상, 0.2% 가 100 ms 이상 늦었다. 실시간
  스레드는 최대 0.6 ms 였다.
- hanyeong 의 실제 누름 기록(16:19~16:40, 225번)에서 50 ms 이상은 1번(100.5 ms, 0.4%)이었다. 위의
  분포와 어긋나지 않는다. 그 기록은 실제 누름이 탭에 닿기까지만 잰다. 전환 한 번에는 다시 보낸 누름과
  뗌도 탭을 지나므로, hanyeong 이 CPU 를 받아야 하는 때는 세 번이다.

## 2026-11-26 18:14: 탭 스레드를 실시간 우선순위로

`hanyeong-tap` 스레드를 `THREAD_TIME_CONSTRAINT_POLICY`(주기 없음, 계산 0.5 ms, 제한 1 ms)로 바꿨다. 실패하면
QoS 37 로 남고 로그에 한 줄 남긴다. 설치본의 `ps -M` 에 `97R` 스레드가 하나 생겼고, 실패 줄은 없었다.

- 바꾸기 직전까지 돌던 37 빌드(16:40~18:13)는 실제 누름 2번, 가장 늦은 것 0.3 ms 였다. 그사이 거의 쓰지
  않아 비교할 거리가 되지 못한다.
- 실시간 빌드에 합성 F19 40번(부하 평균 46~58):

  ```
  hanyeong: 전환 40번, 폭주 차단 0번, 탭 꺼짐 0번
  hanyeong: 한영 키가 hanyeong 에 닿기까지: 40번, 50 ms 이상 0번, 가장 늦은 것 17.6 ms, 잴 수 없음 0번 (0~5 ms 33 · 5~10 ms 3 · 10~20 ms 4 · 20~50 ms 0 · …)
  ```

  probe react 는 중앙값 5.50 ms, p90 14.78 ms, 최대 256.5 ms. passthrough(200회)는 중앙값 2.87 ms,
  p90 9.80 ms, 최대 351.6 ms. 측정 뒤에도 `97R` 스레드는 그대로였다.
- **합성 키로는 효과를 가를 수 없다.** probe 의 탭은 hanyeong 보다 앞에 붙고 우선순위 31 로 돈다. 그래서
  합성 누름의 대기에는 probe 자신이 밀린 시간이 들어 있다(실시간 스레드의 깨어남 지연은 최대 0.6 ms 였다).
  효과는 probe 없이 실제로 누른 키의 기록(`늦게 닿았습니다` 줄, 종료 요약)으로 본다.

## 2026-11-26 18:27: `늦게 닿았습니다` 줄 확인

일부러 늦게 닿는 누름을 만들어 30초마다의 보고가 찍히는지 봤다. 일회용 프로그램 하나가 설치본에 `SIGSTOP`
을 보내고, F19 누름·뗌을 보내고, 약 0.3초 뒤 `SIGCONT` 를 보낸다. 이것을 두 번 했다(짝수 번 전환).

```
hanyeong: 지난 확인 뒤로 한영 키가 늦게 닿았습니다: 50 ms 이상 2번, 가장 늦은 것 431.5 ms
```

- 보고는 찍힌다. 그러니 실제 사용 중에 이 줄이 없으면 그동안 hanyeong 까지 50 ms 넘게 걸린 누름이 없던 것이다.
- 앞선 두 시도는 실패했다: 만든 시각을 200 ms 전으로 적어 보낸 키(시스템이 보낼 때 시각을 다시 적는다.
  보내기 전 `CGEventGetTimestamp` 는 0 이었다)와, 키 보내는 프로그램을 따로 띄운 것(부하 때문에 늦게 떠서
  멈추기 전이나 푼 뒤에 보냈다). 둘 다 대기 4.5~13 ms 로 잡혔다.
- 실시간 빌드에서 사용자가 실제로 누른 7번(18:14~18:21)은 가장 늦은 것이 7.7 ms 였다.
